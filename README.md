# Casting Defect Detection using a Fine-Tuned Vision-Language Model

A reproducible study of one question:

> **How well does a pretrained VLM detect casting defects before fine-tuning,
> and how much does task-specific fine-tuning improve it on unseen images?**

The base model is measured first, the fine-tuned model is measured second on
**exactly the same images with exactly the same prompts**, and the two are
compared. That ordering is enforced in code.

> [!IMPORTANT]
> **The defect-type labels in this dataset are synthetic.** The 11 defect
> classes were generated by painting defects onto real OK castings with a
> script. This project therefore studies detection of *synthetic* defect
> textures. It does **not** demonstrate detection of real casting defects.
> See [`PROJECT_DECISIONS.md`](PROJECT_DECISIONS.md) §1.1.

---

## 1. Project overview

| | |
|---|---|
| **Task** | Binary OK / Defective, plus defect-type identification |
| **Model** | [`Qwen/Qwen3-VL-4B-Instruct`](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct) (Apache-2.0, ungated) |
| **Method** | LoRA / PEFT, vision tower frozen |
| **Dataset** | [`simmoshaikh/casting-defect-detection`](https://www.kaggle.com/datasets/simmoshaikh/casting-defect-detection) — **1,200 labelled images**, 12 classes, 512×512 RGB |
| **Compute** | Analysis on CPU; baseline + training on one NVIDIA GPU (Colab T4/L4) |
| **Seed** | 42 |

## 2. Problem statement

Casting defect inspection is done manually in most foundries: slow, and limited
by human consistency. This project asks whether a general-purpose vision-language
model can perform the OK/Defective judgement, and how much task-specific
fine-tuning helps — while being explicit about what the available labels can
and cannot support.

## 3. Dataset

**Measured on the downloaded files** (not taken from the dataset card):

| Property | Value |
|---|---|
| Labelled images | 1,200 (`output/defect_dataset/`) |
| Classes | 12, exactly 100 each |
| Dimensions | 512×512, uniform |
| Channels | 3 (RGB), JPEG |
| Corrupted | 0 |
| Official split | none — flat class folders |

The card's "1,493 images" also counts `hand_overlays/` (276 unlabelled
renderings) and `visualizations/` (16 plots). Neither is class-labelled, so
both are excluded from analysis, training and evaluation.

**Balance depends on the task.** The 12-way task is balanced (100/class); the
binary task is **1:11 (100 OK vs 1,100 Defective)**. An "always Defective"
classifier scores 91.7% accuracy — read macro-F1 and the confusion matrix,
never accuracy alone.

## 4. Dataset labels

Twelve class folders: `ok`, `cold_shut`, `crack`, `dent`, `flash`, `inclusion`,
`mixed_defects`, `pinhole`, `porosity`, `scratch`, `shrinkage`,
`surface_roughness`.

Anything not `ok` maps to **Defective** for the binary task
(`src/dataset.is_defective_label`). An unrecognised folder name is treated as
defective, never silently as OK.

**These defect types are synthetic** — see the note above.

## 5. Model

`Qwen/Qwen3-VL-4B-Instruct`, loaded with `Qwen3VLForConditionalGeneration` and
`AutoProcessor`. Chosen for being ungated, Apache-2.0, current, and small
enough to fine-tune on a free Colab GPU. Rejected alternatives are documented
in [`PROJECT_DECISIONS.md`](PROJECT_DECISIONS.md) §2.

## 8. Dataset analysis

```bash
python scripts/analyze_dataset.py --data-dir data/raw
```

Writes `dataset_summary.json`, `image_metadata.csv`, and plots for class
distribution, image dimensions and per-class samples into
`results/dataset_analysis/`. Reports corrupted files, duplicate filenames,
byte-identical duplicates and cross-class duplicates.

Then build leakage-safe splits and the training data:

```bash
python scripts/prepare_training_data.py --inspect-groups   # verify grouping first
python scripts/prepare_training_data.py
```

> [!NOTE]
> **Grouping is content-based, not filename-based.** This dataset's filenames
> are per-class counters (`crack_00042.jpg`) that carry no source-casting
> identity — the measured index-match rate against the same-index OK image is
> 2.9%, i.e. chance. But source castings *are* reused across classes (360
> cross-class pairs exceed 0.99 similarity), so images are grouped by
> near-duplicate clustering on pixel content instead. See
> `PROJECT_DECISIONS.md` §1.4. Verified: 854 groups, `verify_no_leakage()`
> passes, worst cross-split similarity 0.9491.

## 9. Baseline experiment (run this BEFORE training)

**The authoritative baseline runs on Google Colab** — see
[`COLAB_SETUP.md`](COLAB_SETUP.md) and
`notebooks/02_base_model_baseline_colab.ipynb`. A 4B VLM needs a CUDA GPU;
Apple MPS is not practical for 534 generations.

On a GPU machine you can also run it directly:

```bash
python scripts/run_baseline.py --limit 5    # smoke test first
python scripts/run_baseline.py              # the real baseline
```

Loads the model with **no adapter**, runs all three prompts over a fixed
class-balanced subset, and writes:

- `results/baseline/baseline_results.csv` — one row per (image, prompt)
- `results/baseline/baseline_raw_outputs.jsonl` — every raw response, streamed
- `results/baseline/eval_subset.json` — **the frozen subset**, reused later
- `results/baseline/baseline_metrics.json`, confusion matrix, `error_analysis.csv`

## 10. Training

```bash
python scripts/train_model.py --sanity-check   # Phase 9: 8 examples, 2 steps
python scripts/train_model.py                  # full LoRA run
```

The sanity check verifies images load, the processor works, labels are masked
correctly, forward and backward passes run, LoRA actually attached (it errors
if zero parameters are trainable), the loss is finite, and the adapter saves.

`train_model.py` **refuses to start a full run without baseline results**.
Everything is configured in [`config/config.yaml`](config/config.yaml).

## 11. Evaluation

```bash
python scripts/evaluate_model.py
```

Reloads the frozen subset (`reuse=True`) and the identical prompts, then writes
`results/evaluation/finetuned_results.csv`, raw outputs, metrics and a
confusion matrix.

## 12. Base vs fine-tuned comparison

```bash
python scripts/compare_models.py
```

Aborts if the two runs do not cover the same (image, prompt) pairs. Produces
`comparison.csv`, `comparison_plot.png`, and `qualitative_comparison.csv`
labelling every image as `both_correct`, `both_wrong`, `fixed_by_finetuning`
or `broken_by_finetuning`.

## 13. New-image testing

## 18. Limitations

- **Synthetic defect labels** — the central caveat (§1.1 of PROJECT_DECISIONS).
- **Class imbalance** — 11 defect folders vs 1 OK folder; read macro-F1 and the
  confusion matrix, not accuracy alone.
- **Uncalibrated confidence** — model-reported, never a calibrated probability.
- **Generalization pending** — until labelled real images are added to
  `data/external/`.
- **Single seed** — no confidence intervals across runs.
- **Not a certified QC system** — research prototype only.

## 19. Future work

- Validate on real casting photographs with verified labels.
- Compare against a CNN baseline (ResNet/EfficientNet), which will likely be
  the stronger and cheaper classifier for this task.
- Calibrate confidence (temperature scaling / verbalised-confidence analysis).
- Repeat over multiple seeds for confidence intervals.
- Defect localisation (bounding boxes or segmentation) rather than
  image-level classification.
